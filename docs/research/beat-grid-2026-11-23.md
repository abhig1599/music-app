## Phase-plan prototype checkpoint

Analysis-only `PhaseTransitionPlanner` now searches a bounded fade-start window
using timestamped outgoing-tail and incoming-head beats. Incoming always begins
at zero and outgoing reaches its natural end. It rejects weak/nonfinite grids,
more than 6% tempo mismatch, sparse overlap, and predicted bidirectional beat
error above 30 ms. This threshold is a design choice, not audible output proof.
There is no downbeat/phrase classifier or playback integration in this change.
Seven pure JVM tests cover shifted phase, tempo direction, full-duration bounds,
irregular beats, weak/invalid confidence, disabled fade and short/unknown duration.
A near-tempo regression exposed floating-point boundary classification; rounding
predicted times to milliseconds before overlap membership fixed that case.

The preceding decoder-window commit failed Android compilation because its
watchdog and first-sample timestamp were scoped inside the codec try block.
Their scope is corrected in this batch; Android CI must confirm the correction.

## Window-to-pair bridge checkpoint

`BeatWindow` converts detector-relative seconds to explicit original-media
milliseconds and preserves measured confidence. `TransitionAnalysis` decodes
outgoing tail and incoming head sequentially, then calls the isolated planner.
Its bounded session cache uses URI, size, modification time, duration and requested
fade. Missing metadata disables cache reuse; metadata is checked again before
storing. Neither the bridge nor the planner is connected to playback yet.
PCM flattening now rejects timestamp discontinuities beyond a 2 ms rounding
tolerance instead of inventing a continuous timeline across a gap/repeated block.
22 pure tests pass locally. Android decoder execution remains unverified.
CI for 2700ab5 succeeded, recorded by e1270c8; the bridge needs its own Android CI.

## Scheduling gate and shadow worker

`PhaseSchedule` checks original-media/wall-clock conversion, incoming-duration
limits and stale/late plans. It rejects plans rather than moving their start or
shortening their overlap while retaining an alignment claim. The 40 ms playback
polling interval is larger than the 10 ms start tolerance in this gate, so this
is not evidence that the current scheduler can deliver accepted plans reliably.
`TransitionWorker` cancellation/duplicate-job tests plus scheduling tests bring
the pure local suite to 27 passing tests. A service shadow path has generation,
queue, duration, toggle and shutdown checks but is disabled by default behind
`phase_shadow`. It does not control audio. Ordinary installs do not incur its
additional decoding work. Phrase/downbeat recognition remains absent.

## One-shot timing and confidence preservation

Pure `TransitionStartTimer` posts a target-time callback rather than waiting for
the 40 ms ramp loop. It cancels replaced callbacks and falls back on stale state
or lateness above tolerance. Four virtual-clock tests cover this logic. It is
not yet connected to audible phase playback, and callback timeliness does not
measure ExoPlayer start latency or the two audio sinks' synchronization.
The existing tempo-only production path now keeps cached confidence instead of
wrapping every cached BPM as confidence 1. Low/nonfinite/out-of-range evidence
falls back to plain crossfade. The pure suite including legacy planner tests
passes 37 tests locally. Android integration tests remain CI-owned.
